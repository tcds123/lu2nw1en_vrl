Define Function Signature, Algorithm, and Constraints, Not Low-Level Details

**When to apply**: For all algorithmic and function implementation tasks. When you care about correctness and performance, not coding style or minor variable naming choices.
**What to do**: Specify the function's name, input parameter types and names, and return type. Clearly state the core algorithmic goal and any hard constraints (time/space complexity, prohibited libraries). Avoid mandating the use of specific variable names, loop types (for vs. while), or intermediate data structures unless critical.
**Example**: "Write a function `def is_anagram(s: str, t: str) -> bool:` that returns `True` if `t` is an anagram of `s`. Your solution must run in O(n) time. Do not use `sorted()` directly; you must count character frequencies."
**Why it works**: Over-specification (e.g., "use a variable named `count_dict`") restricts the model's solution space unnecessarily and can lead to conflicts with its internal patterns. Defining the *what* and *why* (constraints) empowers the model to generate a correct *how* more flexibly and reliably.
