Separate Requirements, Implementation, and Style

**When to apply**: For complex prompts that mix *what* the function must achieve with suggestions on *how* to achieve it and stylistic preferences.
**What to do**: Structure the prompt into distinct sections. First, list the **Requirements**: the immutable, testable behaviors. Then, optionally provide **Implementation Notes**: helpful hints or algorithm names. Finally, state **Style Rules**: coding conventions. Ensure notes and rules do not contradict the core requirements.
**Example**: "Requirements: The function must return the first unique character's index in a string, or -1 if none exists. Implementation Note: Consider using a dictionary for frequency counting. Style Rule: Use a `for` loop with `enumerate`."
**Why it works**: Models can fail when instructions are entangled, treating a suggestion as a hard requirement. This separation prevents confusion, allowing the model to prioritize correctness (requirements) while still benefiting from guidance, without being penalized for choosing a different valid implementation path.
