Balance Specificity with Flexibility for Robust Generation

**When to apply**: When designing a class with multiple methods, or when the problem has valid alternative implementations. Use when you need to enforce a public API and error handling but want to avoid over-constraining internal logic, which can cause the model to generate syntactically invalid or overly rigid code.

**What to do**: Define the required class and method signatures precisely. Specify which exceptions must be raised for invalid inputs (e.g., `ValueError`). For the internal logic, describe the *what* (the required outcome) rather than the *how*, allowing the model to choose appropriate data structures and control flow.

**Example**: "Create a `BankAccount` class with `__init__(self, initial_balance)`, `deposit(amount)`, and `withdraw(amount)` methods. `withdraw` must raise a `ValueError` if `amount` exceeds the current balance. The class must correctly track the balance. Avoid specifying private variable names."

**Why it works**: Over-prescribing minor details (like `self._balance`) can conflict with the model's common patterns, leading to generation failure or unnatural code. This approach secures the essential contract and safety while leveraging the model's ability to fill in standard implementation details correctly.
