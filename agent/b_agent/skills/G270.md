Structure Prompts Around API and Core Logic, Not Low-Level Formatting

**When to apply**: When designing a class, function, or module. When the primary goal is to define a correct interface and algorithmic behavior, not to control the exact string output (like print statements) or minor stylistic choices (like variable naming conventions).
**What to do**: Focus the prompt on the required public methods, their signatures (parameters and return types), and the core logic they must implement. Avoid dictating internal variable names, logging messages, or output formatting unless they are a strict requirement of the problem (e.g., a specific LeetCode output format).
**Example**: "Implement a `Calculator` class with an `evaluate(expression: str) -> float` method that parses and evaluates a string containing integers, `+`, `-`, `*`, `/`, and parentheses. Assume valid input and standard operator precedence. Do not worry about printing the result; just return it."
**Why it works**: Over-specifying low-level details distracts the model from the architectural and algorithmic core of the task. It can lead to code that is rigid, misses edge cases in the logic, or wastes tokens on irrelevant aspects, reducing the quality of the primary solution.
