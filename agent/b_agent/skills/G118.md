Specify Functional Requirements, Not Formatting Rules

**When to apply**: When you need type hints, docstrings, or specific error types, but don't care about line length, variable naming conventions (beyond clarity), or exact comment placement.
**What to do**: Mandate the *presence* and *content* of key structural elements (e.g., "include a docstring describing parameters and return value"). Avoid dictating their style (e.g., "use Google-style docstrings").
**Example**: "Implement the class `DataStore`. It must have an `__init__(self, capacity: int)` method and a `put(self, key: str, value: Any) -> bool` method. Include a class-level docstring and type hints for all methods. The exact formatting of the docstring is not constrained."
**Why it works**: Overly strict formatting rules (e.g., "max 80 chars per line") can cause the model to waste tokens on formatting or, worse, truncate the core logic. This ensures the required code contracts are met while giving the model flexibility to generate syntactically correct code in its preferred style.
