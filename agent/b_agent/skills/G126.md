Define Performance Constraints Without Over-Prescribing Implementation

**When to apply**: When the problem has known algorithmic optimizations (e.g., primality testing, searching sorted data, memoization) but there are multiple valid implementation paths. The goal is to guide the model toward an efficient solution without locking it into a single, potentially error-prone, step-by-step recipe.
**What to do**: State the target complexity class (e.g., O(n log n)) or a key optimization principle (e.g., "check divisors only up to the square root"). Frame it as a *requirement* or *constraint*, not as a series of commands. Do not write pseudocode or mandate specific variable names.
**Example**: "Write a function `is_prime(n)` that returns a boolean. The implementation must have a time complexity better than O(n); specifically, it should not check divisors beyond `sqrt(n)`. Handle `n <= 1` appropriately."
**Why it works**: Models forced to follow rigid step-by-step instructions often produce syntactically incorrect or logically flawed code because they misinterpret a step. By stating the constraint, you allow the model to select a correct internal algorithm (e.g., a `for` loop with `range(2, int(n**0.5)+1)`) that fits its training, leading to more robust and idiomatic code.
