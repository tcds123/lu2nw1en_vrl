Unify Error Handling Strategy and Documentation

**When to apply**: When designing robust APIs or functions where error behavior is part of the contract. Prevents inconsistent behavior where a function sometimes raises and sometimes returns error codes.

**What to do**: Choose one error handling paradigm: *either* raising exceptions (and specify which exception types) *or* returning sentinel values (like `None`, `-1`, a tuple with a status flag). Ensure the function's docstring or comments explicitly describe this chosen behavior and match the implementation.

**Example**: "If the input is invalid (e.g., a negative number), raise a `ValueError` with a descriptive message. Do not return special values like `-1`. The docstring must begin with 'Raises: ValueError: If input is less than 0.'"

**Why it works**: Models may implement ad-hoc error handling, mixing paradigms. A clear, singular directive aligns the implementation with common API design principles and ensures the documented behavior is accurate, which is crucial for users and testers.
