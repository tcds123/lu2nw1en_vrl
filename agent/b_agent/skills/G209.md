Unambiguously Define Function Signature and Naming Conventions

**When to apply**: When the generated code must integrate into an existing codebase, adhere to a specific API, or be assessed by automated tests that check exact function and parameter names. This is a more focused version of G207, specifically targeting naming conflicts.

**What to do**: Declare the exact function name, parameter names, and their order. If the language supports it, include type hints. Explicitly forbid alternative names or signatures. Check that all references to the function within the prompt are consistent and do not introduce synonyms or variations.

**Example**: "Write a function named `parse_config_file(file_path: str) -> dict`. Do not name it `read_config`, `load_config`, or `parse_config`. The parameter must be named `file_path`, not `path`, `filename`, or `fp`. The function must return a Python dictionary."

**Why it works**: Even minor deviations in naming (`get_data` vs. `fetch_data`) or parameter order (`(height, width)` vs. `(width, height)`) cause integration failures and test suite breaks. Models may infer intent and use semantically similar but technically incorrect identifiers if not explicitly constrained.
