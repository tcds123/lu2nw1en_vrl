Ensure Core Problem Specification is Unambiguous and Matches True Requirements

**When to apply**: When the problem involves a key parameter (e.g., shift amount 'k'), a central rule (e.g., "rotate left"), or a behavioral definition. When example inputs/outputs might accidentally imply a more specific rule than intended.
**What to do**: State the core logic in abstract, general terms. Then, use examples *only* to illustrate, not to define, the rule. Explicitly separate the rule from the example to prevent over-fitting.
**Example**: "Rule: Rotate the list `nums` to the left by `k` positions, where `k` is a non-negative integer. Elements shifted past the front should wrap around to the back. Example: For `nums=[1,2,3,4]` and `k=2`, the result is `[3,4,1,2]`. This example illustrates the rule but your code must work for any valid `nums` and `k`."
**Why it works**: Models can latch onto patterns in provided examples. If an example uses `k=2`, they might hardcode logic for that case. This instruction forces the model to internalize the abstract rule, leading to a general solution.
