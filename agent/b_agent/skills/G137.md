Mandate Clean, Modular Solutions Without Over-Restrictive Formatting

**When to apply**: For moderately complex problems where code organization matters (e.g., multiple helper functions, class methods, data validation). Avoid when the problem is trivially short.
**What to do**: Instruct the model to produce a well-structured solution with clear separation of concerns (e.g., validation logic, core algorithm). Use positive directives like "ensure the function is modular" or "include a separate helper function for validation". Avoid negative, absolute formatting commands that could cause refusal (e.g., "never use list comprehensions").
**Example**: "Implement a solution that is clean and modular. Handle invalid input (non-integer, negative numbers) with a clear validation step. The core logic should be readable and not a single, dense block of code."
**Why it works**: Models can produce correct but spaghetti-like code. This guidance encourages maintainable structure. Avoiding overly strict bans prevents the model from failing to generate any code due to perceived conflicting constraints, ensuring you always get an executable solution.
