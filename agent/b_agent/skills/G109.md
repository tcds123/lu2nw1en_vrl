Mandate Self-Contained Functions with Clear Contracts, Not Verbose Restrictions

**When to apply**: When defining the core function for a solution. This is essential for ensuring the output is reusable, testable, and meets the problem's interface requirements without over-constraining the implementation.
**What to do**: Require a single, modular function with a descriptive name and a concise docstring that summarizes parameters, returns, and purpose. Avoid adding ambiguous restrictions (e.g., "do not use loops") that are not part of the core problem statement, as they can confuse the model's logic.
**Example**: "Implement a single function named `calculate_metric` with a clear docstring. The function must be self-contained, accept the specified parameters, and return the required result. Focus the instructions on the function's contract and core logic, not on banning specific implementation techniques unless absolutely necessary."
**Why it works**: Models benefit from a clear, structured target for code generation. Overly verbose or arbitrary constraints can lead the model to focus on the wrong thing (avoiding a technique) instead of solving the problem correctly, potentially resulting in convoluted or incorrect code.
