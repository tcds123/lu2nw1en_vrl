Document successful return type only, not exception paths

**When to apply**: When writing prompts for functions that validate input and raise exceptions on failure.
**What to do**: In the instruction for docstrings and type hints, explicitly state that they should describe the function's behavior *for valid inputs*. The return type hint should not be a `Union` that includes an error type. The docstring should describe the return value and note that specific `ValueError` exceptions are raised for invalid input, but not detail the return value for those paths.
**Example**: "The function's docstring should describe the parameters and the returned value. The `Returns` section should only describe the output for valid inputs. Mention that a `ValueError` is raised for invalid input, but do not document a return value for that case. The type hint for the return should be `-> str`, not `-> Union[str, None]`."
**Why it works**: Models sometimes incorrectly infer that a function can return `None` or an error code on failure, leading to incorrect type hints (`Optional[...]`) and confusing docstrings. This clarifies that exceptions are the sole error-handling mechanism, keeping the interface clean.
