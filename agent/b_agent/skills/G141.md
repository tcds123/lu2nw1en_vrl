Specify Encapsulation Idiomatically, Avoid Mandating Non-Standard Practices

**When to apply**: When designing classes where certain attributes or methods should be internal/private to the class's implementation, following language conventions (e.g., Python's `_single_leading_underscore`).
**What to do**: State the intent (e.g., "these attributes should be treated as protected/private"). Recommend the idiomatic convention for the language. Avoid forcing strict name mangling (e.g., `__double_underscore`) unless it's a specific requirement of the problem, as it can lead to error-prone and awkward code.
**Example**: "Design a `BankAccount` class. The balance should be stored in a private attribute (use the conventional single leading underscore, e.g., `_balance`). Provide public getter methods but no direct setter."
**Why it works**: Models might over-apply strict encapsulation techniques from other languages (like Java-style `private`) to Python, resulting in non-idiomatic and harder-to-debug code (e.g., unnecessary getters/setters for everything). This guides them to use the language's intended mechanisms.
