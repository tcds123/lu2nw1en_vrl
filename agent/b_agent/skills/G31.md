Prioritize core functional correctness (algorithm, input validation) in instructions over stylistic details, and avoid overly restrictive constraints that can cause generation failure.

**When to apply**: When the primary risk is incorrect logic or missing edge cases, not code style. When previous attempts failed because the model got stuck trying to satisfy a minor stylistic rule at the expense of functionality.
**What to do**: Lead with the algorithm, validation, and error handling requirements. Defer stylistic preferences (naming conventions for local variables, exact comment format) to the end or omit them if not critical. Avoid constraints that severely limit standard library use unless absolutely necessary.
**Example**: "Write a function `is_palindrome(s)` that returns `True` if the string `s` is a palindrome, ignoring case and non-alphanumeric characters. Handle empty string input. Implement this logic efficiently." (Style rules like "use snake_case" are implied and less critical than the core logic).
**Why it works**: Over-constraining, especially on style, can force the model into unnatural patterns that break syntax or logic. By focusing on what the code must *do*, you guide the model to a correct solution, which can then be easily refactored for style if needed.
