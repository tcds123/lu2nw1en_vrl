Focus on Functional Constraints Over Stylistic Micro-Management

**When to apply**: When the core challenge is algorithmic correctness, handling edge cases, or data structure integrity, not code appearance. Avoid when style is the explicit requirement (e.g., linter compliance).
**What to do**: Direct instructions toward behavior, performance, and edge case handling. Omit subjective style rules (e.g., "use descriptive variable names") unless they are critical to the problem. Specify *what* the code must do, not *how* it should look.
**Example**: "Implement a function that merges two sorted arrays. The function must run in O(n) time and use O(1) extra space by leveraging the fact that the first input array has sufficient buffer at the end. Handle cases where one input array is empty."
**Why it works**: Models can generate syntactically perfect but logically flawed code if distracted by minor style points. Focusing on functional constraints ensures mental bandwidth is allocated to the hard parts of the problem: logic, efficiency, and correctness.
