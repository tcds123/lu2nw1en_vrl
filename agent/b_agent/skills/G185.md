Focus on Functional Requirements, Not Low-Level Implementation

**When to apply**: When the *outcome* is more important than the specific *path* to get there; to avoid overly restrictive prompts that might conflict with the model's natural coding style or generate syntax errors.
**What to do**: Specify *what* the code needs to accomplish (e.g., "filter the list", "calculate the mean", "find the shortest path"). Avoid dictating *how* to do it (e.g., "use a variable named `temp_result`", "use a list comprehension with an if-else on the left").
**Example**: *Instead of:* "Use a for loop with index `i` and a variable `output_str` to build the result..." *Say:* "Concatenate every second character from the input string."
**Why it works**: Over-specifying syntax can confuse the model or force it into an unnatural pattern that may contain errors. Trusting the model with the implementation details allows it to leverage its vast training data to produce correct, idiomatic code that meets the stated goal.
