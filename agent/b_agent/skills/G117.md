Align Error Handling with Expected Return Type, Not Hidden Tests

**When to apply**: When the problem expects a specific value (like -1, None, or an empty list) on invalid input, rather than a raised exception; when you suspect the model might default to `raise ValueError` without checking the problem's spec.
**What to do**: Explicitly state the required return behavior for edge cases or invalid inputs. Do *not* instruct the model to "raise an exception" unless the problem explicitly requires it. Link the handling directly to the function's signature.
**Example**: "If the input string `s` is empty or contains no digits, the function `extract_numbers(s: str) -> List[int]` should return an empty list `[]`. Do not raise exceptions."
**Why it works**: Models often assume robust code means using `try/except`. If hidden test cases expect a sentinel value but the code raises an exception, the solution will fail. This instruction aligns the model's "safety" instinct with the evaluation criteria.
