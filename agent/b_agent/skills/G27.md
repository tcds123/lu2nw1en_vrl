Explicitly Forbid Common Misinterpretations Alongside Positive Requirements

**When to apply**: When the task's correct behavior is easily confused with a common, default, or intuitive but incorrect behavior. This is critical for tasks involving ordering (e.g., "preserve original order"), uniqueness (e.g., "do not deduplicate"), or transformations that have a standard library equivalent (e.g., "do not use `sorted()`").
**What to do**: First, state the positive requirement clearly. Then, immediately follow it with a negation that explicitly prohibits the specific, likely misinterpretation. Use direct phrases like "do not", "must not", or "avoid". This creates a double boundary around the intended behavior.
**Example**: "The function must preserve the relative order of elements as they appear in the input list. Do not sort the list or alter the original sequence in any way."
**Why it works**: Code generation models often rely on patterns from their training data, which includes many problems where sorting or deduplication is the standard solution. Without an explicit prohibition, the model may apply this common pattern even when it's wrong, because the positive instruction alone is ambiguous.
