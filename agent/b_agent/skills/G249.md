Require a Docstring but Avoid Over-Specifying Implementation

**When to apply**: When code clarity and maintainability are important, or when the function interface is non-trivial. For most function-generation tasks where explanation is beneficial.
**What to do**: Mandate that the function includes a docstring describing the purpose, parameters, and return value. Do not use the docstring to dictate implementation steps, variable names, or algorithmic details. The docstring should describe the *interface*, not the *internals*.
**Example**: "Your solution must include a docstring. The docstring should describe what the function does, the meaning of each parameter, and the return value. For example: `\"\"\"Return the k most frequent elements from the list.\n\nArgs:\n    nums: A list of integers.\n    k: The number of frequent elements to return.\n\nReturns:\n    A list of the k most frequent elements.\n\"\"\"`"
**Why it works**: It enforces good practice and self-documentation without constraining the solution space. Models can generate accurate docstrings from the problem description. Dictating implementation in the docstring is redundant and can conflict with the model's generated code, causing confusion or errors.
