Specify interface, validation, and edge cases, not implementation

**When to apply**: When the problem requires robust handling of invalid inputs or specific edge cases (e.g., number base conversion, matrix operations, API endpoints).
**What to do**: Clearly define the function signature with type hints. List all validation rules and the expected behavior for invalid inputs (typically raising a `ValueError` with a message). Enumerate edge cases (empty input, zero, negatives, large values) and the expected output. Do not describe *how* to implement the core algorithm.
**Example**: "`def convert_base(num_str: str, from_base: int, to_base: int) -> str:`\n- Raise `ValueError` if `from_base` or `to_base` are not between 2 and 36 inclusive.\n- Raise `ValueError` if `num_str` contains characters invalid for the given `from_base`.\n- Handle negative numbers: the input `num_str` may start with '-'; the output must also start with '-'.\n- For valid inputs, return the string representation of the number in the new base."
**Why it works**: Models often neglect input validation unless explicitly told. Prescribing implementation (e.g., "use a while loop") limits creative solution space and can lead to worse code. This focuses the model on the *contract* of the function.
