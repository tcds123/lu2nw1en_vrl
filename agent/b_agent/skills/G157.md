Prioritize Functional Correctness Over Stylistic Restrictions

**When to apply**: When core algorithmic logic is complex and the primary risk is incorrect implementation, not style. When stylistic rules (e.g., "no list comprehensions") might inadvertently rule out the most correct or clear algorithmic approach.
**What to do**: First, exhaustively define the algorithmic behavior, edge cases, and performance requirements. Only then add stylistic preferences, prefaced with language that subordinates them to correctness (e.g., "if possible," "without compromising correctness").
**Example**: "The function `merge_intervals(intervals)` must correctly merge all overlapping intervals in O(n log n) time. Prefer iterative solutions over deep recursion for clarity. **Most importantly, ensure the algorithm is correct for all edge cases, including empty lists and fully overlapping intervals.**"
**Why it works**: Models can get distracted by secondary constraints and produce stylistically perfect but logically flawed code (e.g., avoiding a "forbidden" built-in with a buggy manual implementation). This prioritization ensures the model focuses its capacity on the hardest part: getting the algorithm right.
