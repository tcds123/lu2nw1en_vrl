Balance Core Requirements with Implementation Flexibility

**When to apply**: When the problem requires a specific algorithmic approach (e.g., "use BFS," "must be O(n log n)"), a particular data structure, or has strict complexity constraints, but the exact code path, helper functions, or variable names are not important.

**What to do**: Explicitly state the non-negotiable requirements (algorithm, time/space complexity, prohibited functions). Then, explicitly grant the model freedom in other areas, such as the use of helper functions, specific variable naming, or minor implementation variations, as long as the core constraints are met. This prevents the model from over-constraining itself and missing a simpler valid solution.

**Example**: "Implement a function to find the shortest path in an unweighted graph. You must use Breadth-First Search (BFS) and achieve O(V + E) time complexity. Do not use Dijkstra's algorithm. However, you are free to design your own helper functions, use adjacency list or matrix for the graph representation, and choose any clear variable naming convention."

**Why it works**: Code generation models often fixate on exact phrases from the prompt. Without explicit permission to deviate on non-critical details, they may produce overly rigid or convoluted code that adheres to a misinterpreted "template," or they might reject a valid, simpler implementation that uses a slightly different internal structure. This skill prevents that by clearly separating hard constraints from flexible design space.
