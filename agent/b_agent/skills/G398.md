Tie Error Handling Directly to Stated Methods and Conditions

**When to apply**: When the problem statement specifies invalid inputs, edge cases, or exceptions that must be handled. Do not add generic error handling (e.g., for `None` input) unless specified.
**What to do**: For each method, list the exact conditions under which an error should be raised or a specific value returned. Specify the exact exception type and error message if given.
**Example**: "Implement `def divide(dividend: int, divisor: int) -> int:`. If `divisor` is 0, raise a `ValueError` with the message 'Division by zero'. Handle 32-bit signed integer overflow by returning `2**31 - 1` for positive overflow and `-2**31` for negative overflow."
**Why it works**: Models often either ignore error handling entirely or add excessive, inappropriate checks (e.g., checking for `None` when inputs are guaranteed non-null). This prevents test failures due to unhandled specified errors or unexpected raised exceptions.
