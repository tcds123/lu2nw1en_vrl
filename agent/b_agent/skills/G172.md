Specify Output Format and Docstring, Not Internal Mechanics

**When to apply**: When consistency in documentation or return format is critical (e.g., for API generation, test suite compatibility). When the prompt starts dictating how to name loop variables or which type of loop to use.
**What to do**: Mandate the required docstring format (e.g., Google-style, one-line) and the exact structure of the return value (e.g., "Return a tuple of (result, status_code)"). Explicitly state that internal variable naming and control flow choices are up to the implementation.
**Example**: Instead of: "Write a function to find duplicates. Use a `for` loop called `i` over the list and a `seen` set. Write a detailed docstring." Use: "Write a function `find_duplicates(items: list) -> list`. Include a one-line Google-style docstring summarizing the function. Return a list of duplicate items in the order they were first seen as duplicates. Do not specify implementation details like variable names."
**Why it works**: Over-specifying internal mechanics stifles the model's ability to generate idiomatic or efficient code. By focusing on the contract (docstring and return format), you ensure interoperability while giving the model the freedom to use the most appropriate algorithms (e.g., using a dictionary comprehension vs. a manual loop).
