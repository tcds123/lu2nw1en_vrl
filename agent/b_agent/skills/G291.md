Specify Critical Constraints and Edge Cases with Expected Outcomes

**When to apply**: When the problem domain has known boundaries (like non-negative inputs, sorted lists) or operations that can fail (division, indexing, searching). When robustness is a key requirement.
**What to do**: List the specific constraints (e.g., "`n` will be a non-negative integer") and edge cases (e.g., "if the input list is empty, return `None`"). State *what* should happen in these cases, not *how* to check for them.
**Example**: "The function `find_max(arr)` should return the largest integer in the list `arr`. If the list is empty, raise a `ValueError`. You can assume the list contains only integers."
**Why it works**: Models often generate code that works for the "happy path" but fails silently or crashes on edge cases. Explicitly defining these cases and their required outcomes guides the model to include necessary validation and error handling logic.
