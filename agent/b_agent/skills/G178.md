Prioritize Functional Correctness and Clarity in Instructions

**When to apply**: When the prompt spends excessive words on formatting (indentation, line length), docstring style minutiae, or markdown formatting within the code, rather than on the problem's logic and constraints.
**What to do**: Lead with the functional requirement. If documentation is needed, specify it briefly (e.g., "include a docstring"). Place all non-critical formatting/style requests at the end as secondary notes, or omit them entirely.
**Example**: Instead of: "Write a function. Please use 4 spaces for indentation, not tabs. The docstring must be in triple quotes, with a one-line summary, an `Args:` section, and a `Returns:` section. Make sure lines don't exceed 80 characters. The function should merge two sorted lists." Use: "Write a function `merge_sorted_lists(list1, list2)` that returns a single sorted list merged from the two input sorted lists. Include a brief docstring."
**Why it works**: Front-loading style rules can distract the model's initial attention from the core algorithmic challenge, increasing the chance of logical errors. Models are generally trained on well-formatted code; explicit style rules are often redundant and clutter the prompt.
