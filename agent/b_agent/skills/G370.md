Balance Core Requirements with Implementation Flexibility

**When to apply**: When the problem has a clear "what" (the required outcome) but multiple valid "hows" (implementation strategies), especially in class design, data parsing, or state management problems.
**What to do**: Define the non-negotiable inputs, outputs, and state transformations. Specify invariants that must be maintained. Avoid rules about internal data structures (e.g., "use a queue"), private method names, or specific lines of code unless they are essential to the problem's contract.
**Example**: "Implement a `RateLimiter` class with a `request(timestamp: int)` method that returns `True` if the request is allowed. A maximum of 100 requests are allowed per hour per user. The exact internal tracking mechanism is up to you."
**Why it works**: Overly restrictive implementation rules can prevent the model from generating a correct solution that passes hidden test cases which may rely on a different internal approach. This skill ensures the model's creativity is channeled toward meeting the functional spec, not adhering to arbitrary prescriptions.
