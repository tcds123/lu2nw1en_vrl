Precisely Specify Function Signature, Return Format, and Core Logic

**When to apply**: When the correctness of the solution depends on a specific interface (function name, parameter order and type) and a precise output structure (e.g., a sorted list of tuples, a dictionary with specific keys). This is essential for ensuring the generated code is interoperable and testable against predefined unit tests.

**What to do**: State the exact function name, its parameters with expected types (using type hints if applicable), and the exact return type. Describe the core algorithmic requirement (e.g., "sort by the second element descending, then by the first ascending") and any critical operations (e.g., "slice the result to include only the first 5 items") without providing the implementation code. This guides the logic without overfitting to a single implementation path.

**Example**: "Implement a function `process_records(ids: List[int], scores: List[float]) -> List[Tuple[int, float]]`. The function must pair corresponding `ids` and `scores`, filter out pairs where `score < 60.0`, sort the remaining pairs primarily by `score` in descending order, and secondarily by `id` in ascending order. Return the sorted list."

**Why it works**: Models can correctly implement an algorithm but fail due to a mismatched function name, reversed parameter order, or a return type that is a list instead of a tuple. Explicitly defining the contract separates the "what" from the "how," ensuring the generated code's interface matches the caller's expectations while leaving implementation freedom.
