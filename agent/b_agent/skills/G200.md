Define a Clear, Specific Function Signature with Types and Naming

**When to apply**: For any function generation task, especially when integrating with existing code, when parameter order matters, or when the model might invent inconsistent parameter names.
**What to do**: Provide the exact function definition line, including the `def` keyword, function name, parameter names with type hints (e.g., `: str`, `: List[int]`), and the return type hint. Do not leave naming or typing to the model's discretion.
**Example**: "Provide the code for: `def calculate_discount(base_price: float, discount_percent: float, tax_rate: float = 0.08) -> float:`"
**Why it works**: Without an explicit signature, models often generate plausible but incorrect signatures (e.g., wrong parameter order, different names like `price` vs. `cost`, omitted optional arguments). A precise signature guarantees interoperability and correct test case execution.
