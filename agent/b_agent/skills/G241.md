Balance Specificity with Flexibility for Core Constraints

**When to apply**: When a core constraint is non-negotiable (e.g., recursion, no imports), but the model should still handle reasonable extensions like input validation or helper functions.
**What to do**: State the hard constraint clearly and upfront. Use language that permits, or even encourages, robust supporting code (validation, error handling, helper functions) that adheres to the main constraint.
**Example**: "You must use recursion to calculate the factorial of a non-negative integer `n`. Include input validation to handle negative integers by raising a `ValueError`. You may write helper functions if needed."
**Why it works**: A rigid constraint like "use recursion" can sometimes lead to brittle code that fails on invalid inputs. This guidance ensures the primary requirement is met while generating a more complete, production-worthy function that gracefully handles edge cases within the allowed paradigm.
