Explicitly Define Function Signatures and Structural Requirements

**When to apply**: For any task requiring a specific function, class, or module interface. This is non-negotiable for challenges with automated testers that call functions with exact names and parameter orders.
**What to do**: State the exact function name, parameter names and types, and return type. If helper functions are allowed or required, define their signatures too. Specify if the solution must be within a single function or can include multiple.
**Example**: "Implement a function named `merge_intervals` that takes one parameter: `intervals`, a list of lists of integers. It must return a new list of lists of integers. You may write helper functions if needed, but `merge_intervals` must be the primary, callable function."
**Why it works**: Models sometimes invent their own function names or parameter structures, which causes test suite failures. Explicit signatures ensure the generated code plugs directly into the testing framework.
