## 1. 研究目标与历史事实

### 1.1 原始研究目标

在固定目标模型参数的条件下，通过训练数据中的失败反馈，自动发现新的失败模式、生成多个不同策略、评价候选、组合并累积有效经验，使 Skill 内容、策略模块与搜索结构均可持续进化。

论文主目标是 **training-free Skill 自动进化带来的任务性能提升**。

- Meta-option 是 LiveMath 合法任务组成；自主发现的有效 meta 策略可以正常优化，不设置额外排除门槛。
- 不人工指定最终应出现哪一种数学解题规则，不向 S₀ 或生成器注入 SkillOpt 的已知成功策略。
- SkillOpt 是独立强方法基线，不是自身 Evolver 的组件、教师或候选 donor。
- 当前优先发展 LiveMath；不为了完成任务数量而启动新的大规模 AIME 实验。
- 历史测试数据可以辅助诊断，但不能进入当前搜索数据。由于本研究曾多次接触历史 test=106，正式论文不应称其为整个开发过程从未接触的确认集。

| 统计评估与防退化 | 已有 paired/CI/veto/pool_filter 等 | 保留并审计基准、语义与日志 |

## 2. 完整算法的状态表示

### 2.1 四类状态

| 对象 | 职责 | 必须具备的属性 |
|---|---|---|
| S₀ | 固定初始 Skill | 内容 hash、来源及评估协议 |
| Global Incumbent | 当前整体竞争下保留的最佳 Skill | 完整模块集合、版本、实际评估基准、血缘 |
| Archive | 保存有价值的候选与不同搜索路径 | 不可变 Skill 快照、父节点、候选证据、admission 状态 |
| Adaptive Facet Tree | 组织搜索方向及资源分配 | 动态轴、关联失败模式、模块关联、活跃/停用状态 |

再建立 **Dynamic Slot Registry**：以稳定模块 ID（不以显示标题或段落位置作为唯一身份）管理模块版本、文本、顺序、父代、所属或关联 facet、晋升与继承记录。允许 archive 节点保存不同的完整模块集合；global incumbent 必须引用自己完整、可重建的集合。

### 2.2 两个必须区分的概念

- Facet emergence：创建、细分、合并、停用新的搜索方向。
- Module expansion：创建可执行的新 Skill 策略模块。

两者可以相关，但不能强制一一对应。一个 facet 可以涉及多个模块，一个模块也可以服务多个搜索方向。新 module 晋升不等于已经实现 facet emergence。

### 2.3 生成父代与全局竞争基准

生成父代可以来自 archive，不必永远是 global best；允许保留探索多样性，避免所有分支塌缩。

但必须分别记录：

- `leaf_source_hash`：搜索轴或 leaf 的来源；
- `generation_parent_hash`：实际生成父代（多父时为列表）；
- `incumbent_locked_hash`：本次竞争锁定的 global incumbent；
- `paired_parent_hash`：实际参与配对评估的基准；
- `candidate_hash`：完整候选 Skill；
- `module_lineage`：每个模块的来源、版本与变化。

如果某候选从旧 archive 节点生成，可在 global incumbent 上合成其局部变更，也可以作为明确的整体替换候选进行评估；不能把旧父代中缺少的已晋升模块当作无意的默认丢失。

## 3. 失败模式发现与动态搜索组织

### 3.1 发现流程

1. 在允许使用的 train/select 数据上收集失败、成功及当前 Skill 的覆盖情况。
2. 诊断失败的共享机制，而不仅是 theorem_type 名称。
3. 判断现有模块是否覆盖该机制；区分「已有策略但执行不佳」与「缺少适当策略」。
4. 为有依据的共享失败模式生成多个策略假设。
5. 自主选择 refine、expand、compose，或者创建新的 facet 搜索方向。
6. 根据真实候选反馈调整后续搜索投入。

覆盖驱动 discovery 可以作为 E 首选实现。不要重新强制使用已经被历史证据否定的 theorem_type 聚类键；若该路径仍无法有效发现模式，可以采用另一种由训练失败证据驱动的实现。

### 3.2 动态 facet 管理

- 新轴候选：具有可追溯的共享失败证据，并提出独立、可探索的策略方向。
- 轴激活：具备明确的搜索职责和可执行候选生成路径；可先进入探索池，不要求新轴第一轮就一定产生显著收益。
- 轴合并：两个轴实际解决高度重叠的失败机制时，可提出合并。
- 轴停用：长期缺乏边际贡献、重复搜索或暂时耗尽机会时，可以暂停投入，并保留重新激活的可能。
- 模块删除不是轴停用：已晋升模块即使对应轴被停用，也必须保留，除非有经过整体竞争评估的删除/替换候选。

### 3.3 搜索政策

`n_parallel` 必须真正作用于预期的候选生成路径。至少保留多个角度探索；不能以仅改变随机 seed 却输出相同策略来假装广度。

为结构扩展和组合提供独立探索机会，避免局部 refine 占满全部搜索资源。具体候选数是实验超参数，不写死为算法公理。

不得将某一种合法失败类别永久排除。过去某类别候选负收益，可以作为反馈或资源调度信号，但不能取代对新策略的实际评估。

## 4. 搜索算子规范

| 算子 | 职责 | 约束 |
|---|---|---|
| Refine / facet_edit | 改进指定模块或 slot | 保留原始单 slot 编辑 guard，其他内容从正确父代继承 |
| Expand | 自主新增具有独立功能的策略模块 | 不硬编码禁止 meta 或其他合法类别 |
| Overlay / Compose | 组合互补策略模块 | 记录 donor、组合内容、冲突及来源 |
| Crossover | 在 archive 路径之间交换、重组模块 | 完整候选须重新评估 |
| Joint edit（可选实现） | 协同修改相互依赖的模块 | 明确变化范围，不能绕过全局竞争 |
| Merge / Prune | 合并、删除或简化冗余策略 | 区分搜索轴管理与 Skill 文本修改；后者经过评估 |

### 4.1 本轮 E 必做修改

1. 将 expand 的无条件 meta-skip（报告为 L763，按当前代码查找）移出默认完整算法路径。旧行为可保留为显式 legacy/ablation 开关。
2. 建立动态模块注册、序列化、继承与恢复机制。新 section 晋升后能真正进入下一轮候选。
3. 恢复可生成新 facet 的失败驱动路径，不能仅将创建 section 改名为 emergence。
4. 支持搜索轴合并/停用；支持经过评估的 Skill 模块合并/删除候选。
5. 保留多候选探索、archive 多样性及整体 incumbent 竞争。
6. 验证已有 overlay 是否能读取新增模块 donor，且可以组合、保存、再次使用它们。暂不预设必须重写 overlay；发现具体不兼容才做针对性修复。

### 4.2 暂不做的修改

- 不因为历史 Skill 长度较大就盲目放宽 max_tokens；只有实际截断或容量限制证据才调整。
- 不为了促成 E 的第一个晋升而降低 CI 门槛。
- 不把 SkillOpt 或 theo_iter6 的具体已知规则直接植入候选生成。
- 不将 Skill 变长、模块增加或 facet 增加本身作为性能成功。
- 不在正在运行的 B 或冻结 D 中混入 E 的行为变更。

## 5. 评估、晋升与实验协议

### 5.1 全局竞争

新机制保留 paired_rescore、CI、veto、pool_filter 等有效保护，确认各路径的比较基准和适用语义。

- `delta_incremental = score(candidate) - score(locked_incumbent)`，用于决定全局晋升。
- `delta_global = score(candidate) - score(S₀)`，用于记录整体优化效果。
- 两者不能混用。若全局值并非直接实测，应标注为估计；最终 L2 必须直接与 S₀ 配对。
- 同批候选使用锁定 incumbent。若在批内更新 incumbent，应重新比较或按预先固定的批末选择规则处理，不能沿用相对旧基准的 CI 直接晋升。
- Archive admission 与 global promotion 分开；局部有价值的历史候选不等于允许替换当前全局最优。
- 不直接累加不同轮次的含噪增量充当最终收益。
- 维持题级配对 bootstrap：题内 rollout 聚合后按题重采样，不将 k 次采样当作 k 个独立题目。
- 各算子的全局晋升标准保持一致；若存在基于候选类型的初筛，必须明确记录，不得变成对某合法失败类型的永久禁令。
- 保留每题原始结果、pass rate、delta、CI、基准 hash、拒绝原因及实际调用量。

## 6. 完整算法流程（纯文本与伪代码）

### 6.1 进化流程

```text
固定初始 Skill S₀
    |
    v
Global Incumbent + Archive + Dynamic Slot Registry
    |
    v
在训练/选择数据上收集失败与成功反馈
    |
    v
自主发现共享失败模式、分析现有策略覆盖
    |
    v

    |-- 已有 facet：继续搜索

结束条件达到后：
    冻结最终 Skill -> L2/L3 -> 逐题统计与报告
```

### 6.2 伪代码

```python
S0 = load_frozen_initial_skill()
G = initial_incumbent(S0)
A = initialize_archive(S0)
R = initialize_module_registry(S0)
F = initialize_search_facets()

for iteration in planned_iterations:
    evidence = diagnose(G, optimization_data_only)
    gaps = discover_shared_failure_patterns(evidence, R, F)

    F = manage_search_facets(F, gaps, history=A)
    jobs = allocate_search_jobs(F, gaps, operator_budgets)

    for batch in make_batches(jobs):
        locked = snapshot(G)
        proposals = generate_candidates(
            batch, archive=A, incumbent=locked, registry=R
        )
        candidates = validate_materialize_and_deduplicate(proposals)

        reports = []
        for candidate in candidates:
            report = paired_evaluate(candidate, locked, select_data)
            log_candidate(candidate, report, locked)
            update_archive_if_eligible(A, candidate, report)
            reports.append(report)

        winner = select_eligible_global_winner(reports, locked)
        if winner is not None:
            assert G.hash == locked.hash
            G, R = commit_complete_candidate(winner)
            update_lineage_and_search_feedback(F, A, R, G)

    checkpoint(G, A, R, F, budget, iteration)

final = freeze(G)
evaluate_L2_L3_once(final, S0, frozen_test_manifest)
```

以上伪代码用于约束语义，不要求现有函数必须采用同名接口。若采用并行批次，应保证状态更新原子性；如果全局版本不匹配，进入已定义的重评或批末选择逻辑，而不是继续提交陈旧评估。

## 7. 算法不变量与验收测试

### 7.1 每次代码变更必须满足的不变量

- I01：S₀、模型与数据协议在同一冻结实验内不被静默修改。
- I02：每个候选能重建完整 Skill 及模块血缘。
- I03：无关局部编辑不得意外丢失已晋升模块；有意删除或替换必须作为完整候选记录并竞争。
- I04：所有全局晋升基于正确的 incumbent 及其配对评估结果。
- I05：结构扩展、新轴涌现、局部编辑、搜索轴停用和模块删除具有不同的状态转换。
- I06：合法失败类别不会仅因历史一次负收益被硬编码永久禁用。
- I07：搜索反馈只来自允许的优化数据；test 结果不回流当前运行。
- I08：真实运行可恢复、可审计；缺失历史信息必须明示，不补造。
- I09：归档不同父代用于保持搜索多样性，不能通过局部 admission 绕过全局 promotion。
- I10：关闭 E 的新增行为时应通过 B/D 对照回归检查；不影响运行中的冻结实验。

### 7.2 八项算法级验收

| ID | 能力 | Mock / 确定性验收 | 真实 API 验收 |

| T01 | 自主发现 | 未预设名称的共享失败簇可进入 discovery | 从实际优化失败中提出有证据的策略缺口 |

特别增加以下跨能力测试：

- [ ] B/D 旧模式和 E 模式的独立回归测试。

## 9. 48 小时调度与 API 使用规则

### 9.1 调度约束

已知 B/D/E 共用约 28 RPM 的同一 V3.2 API 额度。不要为了并行而更换 provider/model，也不要让多个长程实验无保护争抢同一 key。

此前 B 实测约 1.6k calls/h，整体曾估计约 38k–40k calls、约 24 小时，但只是运行中的估算。48 小时在这一速率下约可完成 7.7 万次调用，实际因延迟、重试、算子数量和限流变化而不同。D 的调用量需按真实路径重新估计，E 的预算不能照搬 B。

不要承诺 B、D、E、C 全部在 48 小时内结束；计划要优先让有价值的任务始终在执行，并为长程任务保留可恢复交付。

### 9.2 默认长程实验顺序及一次性分支授权

```text
Run B（已经运行，继续）
    |
    +-- 同时进行：规范 / E 开发 / Mock / D 预检 / 离线分析
    |
    v
B 完成并完成必要检查
    |
    v
根据剩余窗口和 E 就绪状态进行一次调度判断
    |
    |-- 正常情况：D -> E smoke -> E full run
    |
    |-- 若 D 尚未启动，E 已通过 Mock，且按真实吞吐估算
    |   先 D 将使 E 连正式启动或有意义的实验进度都难以获得：
    |       E smoke -> E full run -> D
    |   记录此次重排的资源/时间依据，不依据 L2 成绩挑顺序
    |
    |-- E 尚未通过工程验收：
    |       D 使用 API，E 继续离线开发；D 结束后进入 E
    |
    v
合适的短空档：SkillOpt 冻结 Skill 重评（非重跑优化）
    |
    v
E 与核心对照完成后：C / 多 seed / 必要消融
```

**D 已经开始后，原则上不中断健康 D 来腾出时间。** 重排规则仅用于尚未启动的任务；遇到真正故障或冻结硬停例外。

若 E 实现已经就绪而 D 尚未开始，优先用上述明确规则判断是否需要重排，不为了保持字母编号顺序浪费周末。C 不得作为 E 正式启动的前置条件。

按仓库实际时区记录绝对时间与累计时间。以下按周六开始为 T=0，不要求人为等待某个时刻。

- 启动前建立互斥或单一调度所有权，验证同一 key 没有重复长程任务、无重复分发或重复启动。

## 10. 异常处理与自主决策边界

| 情况 | 默认处理 |
|---|---|
| 正常 API 延迟波动 | 保持冻结实验，更新吞吐估计 |
| 持续 429 / 5xx / timeout | 按既有策略退避、降并发或暂停；记录实际请求，避免重试风暴 |
| 健康进程尚未完成 | 不重启、不重复启动，离线并行推进 |
| 实际候选全部不晋升 | 正常研究结果；继续冻结实验，保留证据 |
| 缓存/manifest/hash 不匹配 | 阻止错误评估；修复后仅在可证明一致的情况下 resume |
| E Mock 发现控制流缺陷 | 隔离修复，重新完整验收；API 空档可转到其他就绪任务 |
| E smoke 无显著收益 | 不降低门槛；若工程正确，可启动 full run |
| E smoke 发现关键功能不可达 | 修复实现，重新预检；不假装能力通过 |
| 实验触发硬停止 | 保存可恢复状态和停止原因；根据冻结预算及用户授权决定续跑，不能静默绕过硬停 |
| 某项历史产物不可恢复 | 明确标缺，继续其他分析，不补造 |
| 周末结束时长程 run 未结束 | 保留真实运行状态、checkpoint、监控和 resume 入口，不为交付而杀掉健康任务 |

正常开发、回归、同模型 API 调用及任务顺序切换按本任务书执行，无需逐次请示。不得私自扩展到其他模型、其他账户、未知费用服务或新研究任务。若需提高既定账户限额、改变重大实验协议、处理不可恢复数据风险，或无法在现有环境继续运行，则单独报告并等待相应决定，同时完成其余不受阻任务。
